# MiniSQL 项目技术方案与项目骨架

## 1. 文档目的

本文档用于确定 MiniSQL 数据库系统项目的总体技术路线、工程目录、模块职责和基础工程规范，为后续编码、联调、测试和可视化界面开发提供统一依据。

项目总体目标是实现一个具备 SQL 编译、查询执行、页式存储、索引、事务恢复、权限管理和可视化调试能力的 MiniSQL 系统。

系统处理链路如下：

```text
用户界面/命令行
        ↓
Connector 与会话管理
        ↓
SQL Lexer → Parser → AST → 语义分析
        ↓
逻辑计划 → 规则/代价优化 → 物理计划
        ↓
Executor 执行器
        ↓
Catalog、Transaction、Buffer Pool、Index
        ↓
Page、Extent、Tablespace、Data File
```

## 2. 技术选型

### 2.1 核心服务端

| 类别 | 技术方案 | 选型说明 |
|---|---|---|
| 开发语言 | C++20 | 适合实现数据库底层存储、内存管理、索引和并发控制 |
| 开发工具 | VS Code | 通过 C/C++、CMake Tools 扩展和项目 tasks/launch 配置构建、测试、调试 |
| 编译器 | MSVC 2022 或 GCC 11+ | Windows 开发环境优先使用 MSVC，保证 C++20 支持 |
| 构建工具 | CMake 3.25+ | 支持跨平台构建，并便于组织多模块工程 |
| 依赖管理 | vcpkg | 统一管理第三方库和 Windows 编译依赖 |
| 单元测试 | GoogleTest | 支持模块化测试、测试夹具和参数化测试 |
| 日志 | spdlog | 支持控制台、文件、异步和分级日志 |
| 格式化 | fmt | 提供类型安全的字符串格式化能力 |
| JSON | nlohmann/json | 用于配置文件、API 请求、执行计划和调试结果序列化 |
| 命令行 | CLI11 | 用于启动参数、数据目录、端口和日志级别配置 |
| 内存检查 | AddressSanitizer/Visual Studio Diagnostics | 检查越界、释放后使用和内存泄漏问题 |

### 2.2 网络服务与连接器

服务端采用 C++ 实现，提供本地命令行模式和 Web 服务模式。

| 功能 | 技术方案 |
|---|---|
| HTTP API | Crow 或 Drogon |
| WebSocket | 服务端框架提供的 WebSocket 能力 |
| 数据格式 | JSON |
| 请求模式 | HTTP 用于提交 SQL 和获取结果，WebSocket 用于实时推送执行状态 |
| 认证方式 | 用户名、密码和会话 Token |
| 连接管理 | Connection Manager 统一管理连接、会话和事务上下文 |

如果课程环境不便引入完整网络框架，可以先实现本地 CLI 和函数式 API，再补充 HTTP/WebSocket 服务层。核心数据库模块不得依赖 UI 或网络模块。

### 2.3 可视化前端

| 类别 | 技术方案 | 用途 |
|---|---|---|
| 前端语言 | TypeScript | 提高界面数据模型和 API 调用的类型安全性 |
| 前端框架 | React | 构建 SQL 工作台和可拆分的功能面板 |
| 构建工具 | Vite | 提供快速开发和打包能力 |
| UI 组件 | Ant Design | 提供表格、树、表单、抽屉、标签页等通用组件 |
| SQL 编辑器 | Monaco Editor | 提供代码编辑、关键字高亮和错误定位 |
| 计划图 | React Flow | 展示 AST、逻辑计划和物理计划 |
| 图表 | ECharts | 展示执行耗时、行数、缓存命中率和事务状态 |
| API 通信 | Fetch/Axios + WebSocket | 调用 SQL 服务和接收实时执行信息 |

前端只负责展示、交互和调试信息组织，SQL 解析、语义检查、计划生成和执行必须由服务端完成。

## 3. 总体架构

系统划分为核心库、服务端和前端三部分：

```text
                    ┌──────────────────────┐
                    │ React + TypeScript UI │
                    └──────────┬───────────┘
                               │ HTTP/WebSocket
                    ┌──────────▼───────────┐
                    │ Connector / Server   │
                    │ 会话、认证、权限、API │
                    └──────────┬───────────┘
                               │
┌──────────────────────────────▼──────────────────────────────┐
│                        MiniSQL Core                          │
│ SQL │ Catalog │ Optimizer │ Execution │ Transaction │ Storage │
└──────────────────────────────┬──────────────────────────────┘
                               │
                    ┌──────────▼───────────┐
                    │ Data / WAL / Catalog │
                    │ 数据文件、日志、配置 │
                    └──────────────────────┘
```

依赖方向必须保持单向：

```text
common ← sql/catalog/storage/transaction/execution/optimizer
       ← server
       ← ui
```

底层模块不能反向依赖 `server` 和 `ui`。例如，`storage` 不得包含 HTTP 请求对象，`sql` 不得直接操作 React 或 WebSocket。

## 5. 模块职责

### 5.1 common：公共基础模块

负责所有模块共享的基础能力：

- 基础类型和枚举；
- `Status`、`Result<T>` 和异常类型；
- 配置读取；
- 日志初始化；
- 时间、线程和文件工具；
- 序列化接口；
- 页面 ID、事务 ID、LSN、RID 等公共标识类型。

该模块不得依赖 SQL、存储执行器和网络框架。

### 5.2 sql：SQL 编译模块

负责将 SQL 文本转换为可执行计划前的中间表示：

- Lexer 词法分析器；
- Parser 语法分析器；
- Token 和源代码位置；
- AST 节点；
- 语义分析器；
- 类型检查和名称绑定；
- SQL 错误恢复和诊断信息；
- SQL 格式化和调试输出。

推荐对表达式使用递归下降或 Pratt Parser，并明确以下优先级：

```text
括号 > NOT > 比较运算 > AND > OR
```

### 5.3 catalog：数据库目录和权限管理

负责管理数据库对象及其元数据：

- Database、Table、Column、Index 描述；
- 数据类型和约束；
- 系统目录表；
- 表空间、数据文件和对象位置；
- 用户、角色和权限；
- 表/列/索引查找；
- Catalog 加载和持久化。

Catalog 对外提供稳定查询接口，执行器和优化器不应直接解析 Catalog 文件。

### 5.4 storage：存储引擎

负责数据的物理组织和持久化：

- 数据文件管理；
- Extent 区管理；
- Tablespace 表空间管理；
- Page 页面和 Page Header；
- Slot 槽位和空闲空间；
- Tuple 行记录；
- RID 定位；
- Buffer Pool；
- 脏页刷新和 Checkpoint；
- 文件校验和损坏检测。

存储层不理解 SQL，只提供页面、记录和索引所需的底层读写能力。

### 5.5 execution：执行器和算子

负责执行物理计划：

- Executor 生命周期；
- 算子接口；
- CreateTable、Insert、Delete、Update；
- SeqScan、IndexScan；
- Filter、Project、Sort；
- Aggregate、GroupBy；
- NestedLoopJoin、HashJoin；
- 子查询和 CTE；
- 结果集、列元数据和执行统计。

所有算子应尽量遵循统一接口，例如：

```cpp
class Executor {
public:
    virtual void Init() = 0;
    virtual bool Next(Tuple& tuple, RID& rid) = 0;
    virtual const Schema& OutputSchema() const = 0;
    virtual ~Executor() = default;
};
```

### 5.6 optimizer：查询优化器

负责将逻辑计划转换为更高效的物理计划：

- 逻辑计划和物理计划；
- 优化规则框架；
- 常量折叠；
- 布尔表达式化简；
- 谓词下推；
- 投影裁剪；
- 冗余算子消除；
- 索引条件提取；
- 统计信息；
- 代价估计；
- `EXPLAIN` 和 `EXPLAIN ANALYZE`。

优化器必须提供优化前后的计划输出，方便通过命令行和可视化界面进行对比。

### 5.7 transaction：事务、锁和恢复

负责并发控制和故障恢复：

- Transaction Manager；
- 事务状态和事务 ID；
- Lock Manager；
- 表锁、页锁和行锁；
- 严格两阶段锁；
- WAL 日志；
- LSN 管理；
- Undo/Redo；
- Checkpoint；
- 崩溃恢复；
- 死锁检测或锁超时。

WAL 模块必须独立于具体 SQL 语句，使数据页、Catalog 和索引都可以使用统一的日志机制。

### 5.8 server：Connector、会话和 API

负责把数据库核心能力暴露给命令行和可视化前端：

- Connection Manager；
- Session；
- 用户认证；
- 数据库选择；
- 权限检查；
- SQL 请求分发；
- 参数化执行；
- 请求取消；
- HTTP API；
- WebSocket 推送；
- 结果集和错误信息转换。

建议将一次请求封装为独立的 `QueryContext`，保存用户、数据库、事务、权限和执行统计信息。

### 5.9 ui：可视化界面

实现 SQL 工作台，主要页面和组件包括：

- SQL 编辑器；
- 执行、停止和格式化按钮；
- 结果表格；
- 错误和诊断面板；
- 数据库对象树；
- Token 查看器；
- AST 树；
- 逻辑计划和物理计划图；
- `EXPLAIN ANALYZE` 指标图表；
- B+ 树结构查看器；
- Buffer Pool 页面状态；
- 事务、锁、WAL 和 Checkpoint 监控；
- SQL 历史记录；
- CSV/JSON 导出。

前端组件应通过类型化 API 与服务端通信，并为 Token、AST、Plan、执行统计等结果定义独立的数据类型。

### 5.10 tests：测试模块

测试目录按照测试对象和风险划分：

- `unit/`：单个类或函数；
- `integration/`：多个模块协同；
- `property/`：数据结构和表达式性质；
- `fuzz/`：随机 SQL 和随机字节输入；
- `concurrency/`：并发事务、锁和死锁；
- `recovery/`：WAL、Checkpoint 和崩溃恢复；
- `fixtures/`：初始化脚本、测试数据库和样例数据。

## 6. 基础工程规范

### 6.1 命名规范

- 类型和类名使用 `PascalCase`；
- 函数和变量使用 `camelCase`；
- 常量使用 `kPascalCase`；
- 文件名使用小写加下划线；
- 公共头文件放在 `include/minisql/`；
- 实现文件放在对应的 `src/` 子目录。

### 6.2 异常和错误处理

错误分为以下类别：

```text
LexicalError       词法错误
SyntaxError        语法错误
SemanticError      语义错误
CatalogError       目录错误
StorageError       存储错误
ExecutionError     执行错误
TransactionError   事务错误
PermissionError    权限错误
NetworkError       网络错误
```

面向用户的错误至少包含错误类型、错误码、消息、行号、列号和修复建议。底层异常在跨模块边界时应转换为统一的 `Status` 或业务异常，禁止静默吞掉错误。

### 6.3 日志规范

日志级别统一为：

```text
TRACE → DEBUG → INFO → WARN → ERROR → CRITICAL
```

日志内容应包含时间、级别、模块、线程 ID、事务 ID 或请求 ID。推荐分别记录：

- `server.log`：连接、认证和 API 请求；
- `sql.log`：SQL、解析和语义分析；
- `execution.log`：计划和执行过程；
- `storage.log`：页面、缓冲池和文件操作；
- `transaction.log`：事务、锁和 WAL；
- `recovery.log`：恢复过程。

密码、Token 和完整敏感请求内容不得写入日志。

### 6.4 配置规范

配置文件采用 JSON，至少包含：

```json
{
  "data_directory": "./data",
  "wal_directory": "./data/wal",
  "catalog_directory": "./data/system",
  "page_size": 4096,
  "buffer_pool_size": 128,
  "replacement_policy": "LRU",
  "server": {
    "host": "127.0.0.1",
    "port": 8080,
    "websocket_enabled": true
  },
  "logging": {
    "level": "INFO",
    "directory": "./logs"
  }
}
```

配置优先级建议为：命令行参数 > 环境变量 > 指定配置文件 > 默认配置。

### 6.5 接口规范

模块之间优先使用抽象接口，避免直接依赖实现类。例如：

- `Catalog` 提供目录查询接口；
- `DiskManager` 提供文件页读写接口；
- `BufferPoolManager` 提供页面获取和释放接口；
- `Index` 提供索引操作接口；
- `TransactionManager` 提供事务生命周期接口；
- `Executor` 提供统一迭代接口；
- `Optimizer` 提供计划优化接口。

公共接口变更时必须同步更新测试和设计文档。

## 7. 构建目标

建议至少提供以下 CMake Target：

```text
minisql_common       公共库
minisql_sql          SQL 编译库
minisql_catalog      Catalog 库
minisql_storage      存储引擎库
minisql_execution    执行器库
minisql_optimizer    优化器库
事务恢复由 minisql_execution 与 minisql_storage/PageFile/WAL 共同实现（已删除空的 minisql_transaction 占位目标）
minisql_server       服务端库
minisql              命令行/服务端可执行程序
minisql_tests        GoogleTest 测试程序
```

前端单独使用以下命令：

```text
npm install
npm run dev
npm run build
npm run test
```

服务端建议提供以下启动方式：

```text
minisql --config config/development.json
minisql --data ./data --port 8080
minisql --mode cli
```

## 8. 分阶段落地顺序

### 阶段一：工程基础

完成 CMake、vcpkg、日志、异常、配置、命令行参数和 GoogleTest 基础框架。使用 VS Code 作为统一开发入口，MSVC 作为 Windows 编译工具链。当前实现与验证命令以根目录 readme.md 和 docs/foundation.md 为准。

### 阶段二：SQL 编译前端

完成 Lexer、Parser、AST、错误诊断和基础 SQL 解析测试。

### 阶段三：Catalog 与类型系统

完成表、列、数据类型、约束、索引元数据和系统目录。

### 阶段四：页式存储

完成数据文件、Page、Slot、RID、Extent、Tablespace 和 Buffer Pool。

### 阶段五：基础执行闭环

打通 `CREATE TABLE`、`INSERT`、`SELECT`、`DELETE` 和 `WHERE`。

### 阶段六：执行能力完善

加入 `UPDATE`、NULL、排序、聚合、JOIN、子查询和 CTE。

### 阶段七：索引与优化

完成 B+ 树、Hash 索引、Index Scan、统计信息、规则优化和代价优化。

### 阶段八：事务与恢复

完成锁管理、严格两阶段锁、WAL、Checkpoint、Undo/Redo 和崩溃恢复。

### 阶段九：服务端与权限

完成 Connector、连接管理、认证、权限、HTTP API 和 WebSocket。

### 阶段十：可视化界面

完成 SQL 工作台、结果展示、对象树、Token/AST/Plan 可视化、存储监控和事务监控。

### 阶段十一：综合测试与交付

完成单元、集成、性质、差分、模糊、并发、恢复、性能和 UI 测试，整理部署说明和演示脚本。

## 9. 第一阶段验收标准

完成项目骨架后，应满足以下条件：

1. 执行 `cmake` 可以完成服务端和测试程序构建；
2. 可以通过配置文件指定数据目录、日志目录、页大小和端口；
3. 启动程序后能够输出版本、配置和服务状态；
4. 日志能够写入文件并按级别过滤；
5. GoogleTest 至少有一组可运行测试；
6. 能够通过命令行执行一个最小 SQL 请求；
7. 前端能够启动，并能通过 Mock API 展示 SQL 编辑器和结果面板；
8. 各模块之间的依赖方向符合总体架构；
9. README 中包含构建、测试、启动和目录说明。

## 10. 开发注意事项

- 先实现可运行的最小闭环，再逐步增强底层能力；
- `storage`、`transaction` 和 `catalog` 的接口应尽早稳定；
- 每完成一个模块就补充对应单元测试；
- UI 可以与后端并行开发，但必须通过约定好的 API 数据结构通信；
- 所有计划、Token、AST、执行统计和存储状态都应提供机器可读的 JSON 输出；
- 不允许让调试代码、临时数据和测试账号进入正式发布包；
- 在加入并发、恢复和优化前，先确保单线程基础执行结果正确。
